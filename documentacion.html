1. Descripción General del Sistema

SistemaCC es una aplicación web interna desarrollada para la plataforma Infopuntos, cuyo propósito es centralizar y gestionar los hallazgos de seguridad detectados en los sistemas de la organización. Permite registrar vulnerabilidades, hacer seguimiento de su ciclo de vida, adjuntar evidencias visuales y mantener un historial de auditoría completo de todas las acciones realizadas.

Propósito del sistema

  • Registrar hallazgos de seguridad con nivel de severidad, estado y evidencia fotográfica.
  • Controlar el flujo de remediación de cada hallazgo desde su creación hasta su cierre.
  • Proveer trazabilidad completa mediante logs de auditoría por usuario y acción.
  • Gestionar los usuarios del sistema con control de acceso por rol.
  • Exportar reportes en formato PDF con gráficos de distribución.

Tipo de aplicación

Aplicación Web de Página Única (SPA/SSR)

Construida con Next.js App Router, combina renderizado en servidor (Server Components) y en cliente (Client Components) según la necesidad de cada módulo.

Acceso por roles

Tres niveles de acceso: Super-Admin, Admin y Analista. Cada rol tiene permisos específicos tanto en la interfaz como en el middleware del servidor.

Backend serverless

No requiere servidor propio. Toda la lógica de datos se resuelve a través de Firebase (Auth, Firestore, Storage), que actúa como backend-as-a-service.

Seguridad por capas

Cookies firmadas criptográficamente, CSP, HSTS, middleware de rutas, sanitización de entradas y logger silencioso en producción.

3. Sistema de Roles y Permisos

El sistema implementa control de acceso basado en roles (RBAC) con tres niveles. Los roles se almacenan en Firestore (campo cargo del documento de usuario) y se validan tanto en el middleware del servidor como en los componentes de la interfaz.

Rol Módulos accesibles Capacidades
super-admin Todos los módulos
  • Todo lo que puede Admin
  • Puede cambiar estado de admins y analistas
  • No puede ser desactivado por otros roles
  • Único rol que puede gestionar admins
admin Dashboard, Hallazgos, Auditoría, Usuarios, Registro
  • Crear, editar y eliminar hallazgos
  • Ver y filtrar logs de auditoría
  • Registrar nuevos usuarios (analistas)
  • Activar/desactivar analistas
  • Exportar PDF de hallazgos
analista Dashboard, Hallazgos (lista y detalle), Nuevo hallazgo
  • Crear nuevos hallazgos
  • Ver y editar hallazgos existentes
  • Adjuntar imágenes de evidencia
  • Sin acceso a auditoría, usuarios ni registro
¿Cómo se aplica el control de roles? El rol viaja en una cookie rol firmada con HMAC-SHA256. El middleware proxy.ts verifica criptográficamente esa firma antes de permitir acceso a rutas admin-only. Si la firma no coincide (cookie tamperada), el acceso es denegado.

→

→

→

→
Middleware verifica firma en cada ruta

4. Módulos y Funcionalidades

4.1 Autenticación y Sesión

Archivo: components/login.tsx, lib/api.ts, lib/sesion.ts

El proceso de autenticación sigue estos pasos:

  1. El usuario ingresa correo y contraseña en el formulario de login.
  2. Se llama a loginUser(email, password) en lib/api.ts.
  3. Se autentica contra Firebase Authentication con signInWithEmailAndPassword.
  4. Se consulta Firestore para obtener los datos del usuario (nombre, cargo, estado).
  5. Si el usuario está inactivo, se rechaza el acceso con mensaje apropiado.
  6. Se invoca la Server Action setSession(uid, cargo) que establece las cookies httpOnly firmadas.
  7. Se registra el evento LOGIN en los logs de auditoría.
  8. Se redirige al panel de control.

Para cerrar sesión, se llama a logoutUser() que:

  • Registra el evento LOGOUT en auditoría.
  • Cierra la sesión de Firebase con signOut(auth).
  • Elimina las cookies de sesión con la Server Action clearSession().
Nota sobre la validación del formulario El formulario de login usa React Hook Form con validación Zod. Los errores de Firebase (credenciales incorrectas) se mapean a mensajes genéricos para no revelar si el correo existe o no en el sistema.

4.2 Panel de Control (Dashboard)

Archivo: app/(barra)/panel-admin/page.tsx

Es la pantalla principal tras el login. Muestra un resumen ejecutivo del estado actual de los hallazgos de seguridad:

  • Tarjetas de métricas: Total de hallazgos, hallazgos críticos, en remediación y cerrados.
  • Tabla de hallazgos recientes: Los últimos 5 hallazgos con severidad y estado resaltados con colores semánticos.
  • Accesos rápidos: Botones para nuevo hallazgo, lista completa, auditoría (admin+), crear usuario (admin+) y gestión de usuarios (admin+). Los botones de admin se ocultan dinámicamente para analistas.

4.8 Registro de Nuevos Usuarios

Archivo: app/(barra)/panel-admin/register/page.tsx

Acceso restringido a: admin, super-admin

Formulario para crear cuentas nuevas. Proceso técnico:

  1. Crea el usuario en Firebase Auth usando una aplicación Firebase secundaria temporal, lo que evita que la sesión del administrador actual sea reemplazada.
  2. Cierra la sesión de la app secundaria y la destruye.
  3. Crea el documento en Firestore (users/{uid}) con los datos del perfil.
  4. El administrador puede asignar los roles: analista (por defecto) o admin.
  5. Solo super-admin puede crear otros super-admins.
Política de contraseñas La contraseña debe tener mínimo 8 caracteres, al menos una letra mayúscula, una minúscula, un número y un carácter especial. La confirmación de contraseña se valida del lado del cliente antes de enviar a Firebase.

5.3 Firebase Storage

Las imágenes de evidencia se almacenan en la ruta:

findings/{findingId}/{uuid}.{ext}

Donde uuid es un identificador criptográficamente aleatorio generado con crypto.randomUUID() (no predecible ni enumerable). La extensión se deriva del MIME type real del archivo, nunca del nombre original.

El proceso de validación de imágenes antes de subir:

  1. Cliente: Verifica que el tipo MIME declare ser una imagen y que el tamaño sea ≤ 5 MB.
  2. Servidor: Lee los primeros 4 bytes del archivo (magic bytes) para confirmar el formato real (JPEG: FF D8, PNG: 89 50 4E 47, GIF: 47 49 46, WebP: 52 49 46 46).

6. Medidas de Seguridad Implementadas

6.1 Protección de cookies con HMAC-SHA256

Archivo: lib/sesion.ts

Las cookies de sesión (token y rol) se firman criptográficamente antes de almacenarse. El formato es:

valor.HMAC_SHA256(valor, SESSION_SECRET)_en_base64url

Esto impide que un atacante que modifique su cookie (por ejemplo, cambiando rol=analista a rol=admin) pueda engañar al sistema, porque la firma ya no coincidiría. El middleware verifica esta firma en cada petición.

Propiedades adicionales de las cookies:

  • httpOnly: Inaccesibles desde JavaScript del navegador (protege contra XSS).
  • sameSite: strict: Solo se envían en peticiones originadas desde el mismo dominio (protege contra CSRF).
  • secure: Solo se transmiten por HTTPS en producción.
  • maxAge: 3600: Expiran automáticamente tras 1 hora.
  • path: /: Válidas para toda la aplicación.
Acción requerida en despliegue Definir la variable de entorno SESSION_SECRET con una cadena aleatoria de al menos 32 caracteres. Sin ella, las firmas se generan con clave vacía y no ofrecen protección real.

6.2 Middleware de protección de rutas

Archivo: proxy.ts

El middleware intercepta todas las peticiones a rutas protegidas antes de servirlas. La lógica de decisión:

CondiciónAcción
Sin cookie token válida + ruta protegidaRedirige a /login
Con sesión válida + intenta acceder a /loginRedirige a /panel-admin
Rol no es admin/super-admin + ruta admin-onlyRedirige a /panel-admin
Cookie con firma inválidaTratada como si no existiera (denegado)

Rutas protegidas como admin-only:

  • /panel-admin/auditoria y subrutas
  • /panel-admin/usuarios y subrutas
  • /panel-admin/register y subrutas

6.5 Cache Control en rutas sensibles

Todas las rutas bajo /panel-admin y /panel-admin/* incluyen:

Cache-Control: no-store, no-cache, must-revalidate, proxy-revalidate
Pragma: no-cache

Esto impide que los datos sensibles (hallazgos, logs, usuarios) queden almacenados en el caché del navegador, CDN intermediarios o dispositivos compartidos.

6.6 Sanitización de entradas de usuario

Archivo: components/hallazgos/hallazgo-form.tsx

Antes de persistir cualquier dato en Firestore, los campos de texto son procesados por:

str
  .replace(/<[^>]*>/g, "")          // Elimina etiquetas HTML completas
  .replace(/\bon\w+\s*=\s*["']?[^"'>]*/gi, "") // Elimina atributos de evento (onclick, onerror, etc.)
  .replace(/javascript\s*:/gi, "")  // Elimina javascript: URIs
  .trim()
¿Por qué no solo escapar < y >? La sanitización previa solo escapaba los signos menor/mayor, lo que no bloqueaba vectores como onerror="alert(1)" o href="javascript:void". La nueva sanitización elimina el payload completo.

6.7 Validación de archivos subidos

Las imágenes de evidencia pasan por doble validación:

  • Lado cliente: Tipo MIME declarado debe comenzar con image/ y tamaño ≤ 5 MB.
  • Lado servidor (lib/api.ts): Verificación de magic bytes (primeros 4 bytes del archivo binario), comparados contra las firmas reales de JPEG, PNG, GIF y WebP. Un atacante que renombre un ejecutable como .jpg será rechazado.

6.9 Logger silencioso en producción

Archivo: lib/logger.ts

Todos los métodos del logger (error, warn, log) son funciones no-op en producción. Esto evita filtrar trazas de stack, rutas internas, nombres de dependencias o mensajes de error técnicos a la consola del navegador, que podría ser explotada por un atacante para obtener información del sistema.

6.10 Validación de rol en contexto React

Archivo: lib/auth-context.tsx

El campo cargo obtenido de Firestore se valida contra la lista de roles conocidos antes de asignarse al contexto:

const VALID_ROLES: Rol[] = ["super-admin", "admin", "analista"];
setRol(cargo && VALID_ROLES.includes(cargo as Rol) ? (cargo as Rol) : null);

Si el campo cargo contiene un valor no reconocido (por manipulación de BD o error de datos), el rol en el contexto se establece en null en lugar de propagarse como un rol válido.

8. Variables de Entorno

Crear un archivo .env.local en la raíz del proyecto con las siguientes variables:

# ── Firebase (configuración del proyecto) ──────────────────────────
NEXT_PUBLIC_FIREBASE_API_KEY=AIza...
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN=tu-proyecto.firebaseapp.com
NEXT_PUBLIC_FIREBASE_PROJECT_ID=tu-proyecto
NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET=tu-proyecto.appspot.com
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=123456789
NEXT_PUBLIC_FIREBASE_APP_ID=1:123:web:abc...

# ── Seguridad de sesión ──────────────────────────────────────────────
# Cadena aleatoria de mínimo 32 caracteres para firmar cookies HMAC-SHA256
# Generar con: openssl rand -base64 32
SESSION_SECRET=TuClaveSecretaMuyLargaYAleatoriaAqui
Variables NEXT_PUBLIC_* Las variables con prefijo NEXT_PUBLIC_ son expuestas al navegador. Las claves de Firebase con este prefijo son necesarias para que el SDK del cliente funcione. Su seguridad depende de las reglas de Firestore y Firebase Security Rules, no de que estén ocultas.
SESSION_SECRET — Solo servidor Esta variable NO debe tener el prefijo NEXT_PUBLIC_. Solo está disponible en el servidor (Server Actions, middleware). Nunca llega al navegador.

9. Flujo de Estados de un Hallazgo

Cada hallazgo sigue un ciclo de vida lineal y unidireccional. No se permite retroceder a un estado anterior, lo que garantiza la integridad del proceso de remediación.

Estado Color Significado Acciones disponibles
Nuevo ■ Índigo Hallazgo recién registrado, pendiente de análisis Avanzar a "En análisis", editar campos
En análisis ■ Azul El equipo está evaluando el impacto y vector del hallazgo Avanzar a "En remediación", editar campos
En remediación ■ Ámbar Se está aplicando la corrección o mitigación Avanzar a "Mitigado", editar campos
Mitigado ■ Verde La vulnerabilidad ha sido atendida y se espera confirmación Avanzar a "Cerrado", editar campos
Cerrado ■ Gris Hallazgo resuelto y verificado. Estado terminal Solo lectura

Cada transición de estado se registra en dos colecciones:

  • finding_history: campo "estado", valor anterior, valor nuevo, quién y cuándo.
  • audit_logs: evento CAMBIO_ESTADO con detalle del cambio.

# Crear .env.local con las variables descritas en la sección 8
